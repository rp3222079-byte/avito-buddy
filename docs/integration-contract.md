# Предлагаемые границы интеграции

Черновик для согласования с Даней и Степаном. По умолчанию приложение запускается на демоданных. С `VITE_API_MODE=real` оно запрашивает `GET /api/jira/tasks` и `GET /api/mentor/interns` на том же origin, с cookies текущей сессии. Ответы ожидаются в виде объектов с массивом `tasks` или `interns`, как в файлах `data/`. Ошибки чтения показываются в соответствующей панели.

## Данные, которые уже использует интерфейс

- Профиль: отображаемое имя, команда, роль, наставник. Сейчас фиксированные демоданные.
- Квест: `id`, `title`, `description`, награда и статус `available | pending | done`.
- Сообщение: `id`, `role`, `text`, источники и действия. Markdown отображается в ответах Бадди.
- Заявка: `id`, `resource`, `reason`, статус `draft | pending | approved`.
- Ответы с источниками: заголовок, текст, идентификатор документа; сейчас статические статьи.

## Чат по SSE

В сетевом режиме frontend отправляет `POST /api/chat`. Путь можно переопределить через `VITE_CHAT_PATH` при запуске Vite или сборке. Запрос содержит `Content-Type: application/json`, `Accept: text/event-stream` и `Idempotency-Key`. Тело запроса выглядит так:

```json
{"message":"Как получить доступ к Confluence?"}
```

При открытой переписке со стажёром frontend добавляет `intern_id`. Backend определяет роль и автора по сессии, проверяет право на переписку и трактует `intern_id` как адресата.

Ответ имеет статус 200 и `Content-Type: text/event-stream; charset=utf-8`. Каждое событие заканчивается пустой строкой. Сервер и прокси должны отдавать события по мере готовности, с отключённой буферизацией. Пример полного ответа:

```text
event: delta
data: {"text":"Могу создать "}

event: delta
data: {"text":"заявку на доступ."}

event: done
data: {"sources":[],"tools_used":[],"actions":[{"type":"button","id":"create_access_ticket","label":"Создать заявку","data":{"system":"Confluence"}}]}

```

- `delta` добавляет `text` к уже показанному ответу.
- `done` завершает поток. Опциональный `reply` заменяет накопленный текст, если сервер присылает итоговую версию. Здесь же приходят источники и действия. Карточку уже созданной заявки можно вернуть в `actions` как `{"type":"card","kind":"ticket","data":{"ticket_id":"IT-123","status":"created","sla_hours":2}}`.
- `error` завершает поток с ошибкой. Пример данных — `{"message":"Бадди не успел ответить. Попробуй ещё раз."}`. Используй текст для пользователя. Для ошибок до начала потока верни соответствующий HTTP-статус.

EOF до `done` считается обрывом. На один запрос отведено 60 секунд. При ручном повторе frontend использует тот же ключ идемпотентности. Backend должен использовать ключ в пределах сессии, чтобы повтор возвращал тот же результат без дублирования записи или побочных эффектов. Доставка автоматического утреннего брифинга требует отдельного контракта.

## Подтверждение действий

Клик по кнопке из `done.actions` отправляет JSON и `Idempotency-Key`. Повтор после ошибки использует тот же ключ.

| Действие | Запрос | Успешный ответ |
| --- | --- | --- |
| `create_access_ticket` | `POST /api/jira/ticket` с `{"system":"Confluence"}` | `{"ticket_id":"IT-123","status":"created","sla_hours":2}`. Для существующей заявки верни её данные. |
| `notify_mentor` | `POST /api/notify-mentor` с `{"message":"Проверь задачу AVT-555"}` | `204 No Content` или успешный JSON-ответ. |

Сервер проверяет права и параметры действий, определяет стажёра и наставника по сессии и обеспечивает идемпотентность. Frontend показывает карточку заявки и подтверждение отправки после успешного ответа.
