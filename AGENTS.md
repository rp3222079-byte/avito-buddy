## 1. Контекст проекта

Avito Start — веб-приложение, которое помогает стажёрам проходить адаптацию, а наставникам отслеживать их прогресс.

Основные функции:

- AI-чат для вопросов по базе знаний компании.
- Отображение ответов AI в потоковом режиме (SSE).
- Интерактивные карточки заявок и задач.
- Кнопки быстрых действий.
- Утренние брифинги с задачами.
- Дашборд наставника с информацией о стажёрах.
- Разграничение интерфейсов по ролям.
- Обработка ошибок API и сети.

## 4. Мои основные задачи

### A. Чат с AI

Реализовать интерфейс чата:

- История сообщений.
- Поле ввода.
- Отправка сообщений.
- Потоковое отображение ответа через SSE.
- Индикатор генерации.
- Markdown в ответах.
- Прокрутка к новым сообщениям.
- Кнопка повторной попытки.
- Обработка обрыва соединения.
- Корректная очистка потоков при размонтировании компонентов.

Не предполагай формат SSE-событий, пока он не согласован с Backend.

### B. Интерактивные элементы

Поддержать формат ответа AI:

```json
{
  "reply": "Текст ответа",
  "sources": [],
  "tools_used": [],
  "actions": [
    {
      "type": "button",
      "id": "notify_mentor",
      "label": "Отправить напоминание"
    },
    {
      "type": "card",
      "kind": "ticket",
      "data": {
        "ticket_id": "IT-123",
        "sla_hours": 2
      }
    }
  ]
}
```

Создать расширяемую систему компонентов для отображения `actions`.

Обязательные компоненты:

- ActionButton
- TicketCard
- ChatMessage
- ChatInput
- MessageList
- StreamingMessage

Кнопки должны выполнять реальные действия через API либо явно обозначенные mock-обработчики.

### C. Дашборд наставника

Создать страницу наставника с:

- Таблицей стажёров.
- Именами.
- Процентом прогресса.
- Статусами.
- Списком блокеров.
- Фильтрацией.
- Сортировкой.
- Переходом к чату со стажёром.

Статусы:

- `blocked` — красный.
- `at_risk` — жёлтый.
- `on_track` — зелёный.

Интерфейс должен быть адаптивным.

### D. Роли и маршрутизация

Две роли:

- `intern` — стажёр.
- `mentor` — наставник.

Стажёр не должен видеть дашборд наставника.

Реализуй защиту маршрутов на уровне UI.

Помни, что настоящую проверку прав выполняет Backend. Frontend-защита не заменяет серверную авторизацию.

Для разработки используй временный переключатель ролей.

### E. Обработка ошибок

Предусмотри:

- Backend недоступен.
- AI не отвечает.
- Превышено время ожидания.
- Нет интернет-соединения.
- Ошибка 403.
- Пустые данные.
- Не удалось создать заявку.
- Прерван SSE-поток.

Используй Error Boundaries для ошибок рендеринга и отдельную обработку ошибок сетевых запросов.

Не допускай белого экрана при сбоях.

## 5. Независимая разработка Frontend

Backend разрабатывается параллельно.

Поэтому Frontend должен работать автономно на mock-данных.

Требования:

1. Создай единый слой взаимодействия с API.
2. Отдели UI от получения данных.
3. Используй TypeScript-интерфейсы для API.
4. Реализуй mock-адаптеры.
5. Предусмотри переключение между mock и real API через конфигурацию.
6. Не размещай mock-данные непосредственно в JSX.
7. Не привязывай компоненты к конкретной реализации Backend.
8. Для SSE предусмотрите отдельный mock-поток, имитирующий поступление фрагментов текста.

Желаемый результат: после готовности Backend мы заменяем адаптеры и подключаем реальные эндпоинты без масштабной переработки компонентов.

## 12. Выводы Q&A по кейсу AI Buddy

Источник — `Avito_AI_Buddy_QA_review.pdf`, с. 1–5, сводка вебинара Hack&Change 2026 с Маратом, тимлидом внутренних разработок Авито. Сводка основана на автоматической расшифровке. Порог покрытия, правила его расчёта и порядок предоставления LLM-ключа нужно сверить с официальными материалами или организаторами. Примеры сценариев и полей из Q&A обсуждаются командой и сами по себе не задают API-контракты.

### Фокус MVP и сценарии

- Выбрать основную аудиторию и измеримую цель: быстрее довести новичка до первой самостоятельной задачи или сократить нагрузку наставника. Для стажёра первична самостоятельность. Сценарии стажёра применимы и к другим новичкам с поправкой на опыт. Прогресс, статусы и уведомления наставника или руководителя дополняют путь новичка. Чек-лист бэкендера служит примером, у команд могут быть свои чек-листы.
- Составить CJM первых двух недель: оборудование и доступы, ориентация в процессах и системах, чек-лист, адаптационные встречи, первая самостоятельная задача. После опроса или брейншторма выбрать 3–5 сквозных сценариев. Ориентир для пяти — два простых, два средних и один сложный. Один глубоко проработанный сценарий допустим, его вес относительно 3–5 сценариев жюри не уточнило.
- Считать сценарий завершённым, когда новичок решил задачу или прошёл конкретный шаг CJM. Для ноутбука показать сроки, способ получения, необходимость поездки в офис и доступные действия до выдачи. Для Grafana можно дать практику: найти дашборд, посчитать response time, собрать свой дашборд.
- Критерии жюри использовать как ориентир. Демо должно показывать рабочую логику и пользу сквозного сценария. Чат поверх чек-листа закрывает базовую справку. Для демонстрации достаточно одного рабочего экрана с чатом, планом и карточками либо бота в мессенджере. Агент в существующей платформе упрощает внедрение, отдельный продукт тоже допустим.

### Что включить в гипотезы для базы знаний

- Новички чаще спрашивают «что» и «как». Подтверждённого топ-5 нет. Начать с оборудования и инфраструктуры: ноутбук, внутренняя сеть, почта, загрузка документов, согласия, ЭЦП/ЭДО.
- В разработке проверить путь от репозитория до релиза: PR и ревьюеры, dev-стенд и свой стенд, запуск микросервисов, тесты, quality gates, CI/CD, логи и ключи, упавший pipeline и комментарии ботов, код-стайл и архитектура команды.
- В HR проверить цели, ИПР, чек-лист, отпуск и отгул, обучение, командировки и компенсации. Типичный рабочий контекст включает Mattermost, Jira, Confluence, Grafana, Redash, Bitbucket, Docker/Kubernetes, внутренние DevOps- и заявочную системы. Возможные вложения: скриншоты, логи, документы, ссылки, видео и пересланные сообщения.
- Базовые доступы (Jira, VCS, Confluence) обычно входят в чек-лист. Более сложные вопросы идут наставнику из-за разрозненной или недоступной документации и отсутствия контекста применения. Основные задержки и повторы — код-ревью и Ops от постановки задачи до релиза. Наставника особенно нагружают сложный запуск микросервисов, командные правила в коде и ответы LLM, полученные без понимания задачи.
- Единого инженерного плейбука нет. Общие и командные инструкции можно сочетать. Для демонстрационных материалов подходят открытые плейбуки и публикации, например на Хабре. Промпты команда выбирает сама, RCTF приведён как пример. Внутренние промпты и feature flags публично не описаны.

### Поведение, действия и доступ к данным

- Для действий с последствиями предусмотреть подтверждение человеком. Команда определяет, какие операции помощник предлагает и какие выполняет после подтверждения. Для заявки описать проверяемый сценарий: какие данные пользователь видит и подтверждает, что уходит через API, какой статус показывается после отправки и где заканчивается сценарий.
- Устаревшие и противоречивые инструкции явно помечать. Рассмотреть уведомление наставника или руководителя о проблемном источнике. При отсутствии инструкции маршрут эскалации из Q&A — наставник, руководитель, затем HRBP для организационных вопросов. Интернет обсуждался как последний источник общей справки. Адаптация на протяжении всего испытательного срока выходит за рамки помощи ИИ, описанной экспертом.
- Для доступа использовать настраиваемые пресеты. Примеры полей — проект или ключ, обоснование, read/write/admin, пространство или страница, подписка на типы задач, дополнительные поля ресурса. Согласующий зависит от ресурса: владелец проекта, страницы или пространства, тимлид, DevOps, руководитель, архитектор либо руководитель кластера. Команда выбирает финальное состояние: отправлено, получено уведомление или доступ выдан.
- Отгул, отпуск и больничный моделировать как отдельные процессы существующей HR-системы. В отчёте упомянуты согласование руководителем с участием HR-админа/HRBP, сроки по ТК РФ и возможность читать статусы. Конкретные правила и поля согласовать перед интеграцией.
- Предусмотреть RBAC/ABAC с атрибутами доступа к своим данным, данным подчинённых и данным в зоне ответственности руководителя. Проверка прав выполняется на сервере. Чужая зарплата и сведения о ДМС закрыты для стажёра. Внутреннюю матрицу настроит Авито, а GCP IAM и AWS IAM в отчёте приведены как ориентиры.
- Для демо использовать синтетические данные и открытые аналоги. Возможный контекст сотрудника — команда, роль, руководитель, HRBP, T&D-партнёр, контакты, чаты, локация, репозитории, проекты, балансы обучения или лояльности. Команда определяет, какие атрибуты действительно нужны для персонализации, например локация для рабочего календаря или предпочтения по стилю общения. Справка по финансам и бенефитам допустима, операции можно мокать. Реальные финансовые данные и примеры ролевой модели не обещаны, деперсонализация остаётся у Авито.

### Внедряемость и сдача

- Внедряемость названа самым весомым критерием. Проверяющие читают код, запускают Docker и проверяют приложенные данные. Ориентир — запуск одной командой и работа без гарантированной GPU. По отчёту, загрузки из интернета допустимы, офлайн-режим годится как резерв.
- Настраивать LLM-провайдера через конфигурацию, в README указать провайдера и шаги подключения ключа. По предварительной трактовке Q&A, проверяющие создают ключ сами. Допустимы разные языки, фреймворки, зарубежные API и локальные модели. Локальная модель может дать небольшой плюс, использовать проверенные источники весов. Для дообученной модели можно приложить датасет.
