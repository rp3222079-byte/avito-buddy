## 1. Контекст проекта

Avito Start — веб-приложение, которое помогает стажёрам проходить адаптацию, а наставникам отслеживать их прогресс.

Основные функции:

- AI-чат для вопросов по базе знаний компании.
- Отображение ответов AI в потоковом режиме (SSE).
- Интерактивные карточки заявок и задач.
- Кнопки быстрых действий.
- Утренние брифинги с задачами.
- Дашборд наставника с информацией о стажёрах.
- Разграничение интерфейсов по ролям.
- Обработка ошибок API и сети.

## 4. Мои основные задачи

### A. Чат с AI

Реализовать интерфейс чата:

- История сообщений.
- Поле ввода.
- Отправка сообщений.
- Потоковое отображение ответа через SSE.
- Индикатор генерации.
- Markdown в ответах.
- Прокрутка к новым сообщениям.
- Кнопка повторной попытки.
- Обработка обрыва соединения.
- Корректная очистка потоков при размонтировании компонентов.

Не предполагай формат SSE-событий, пока он не согласован с Backend.

### B. Интерактивные элементы

Поддержать формат ответа AI:

```json
{
  "reply": "Текст ответа",
  "sources": [],
  "tools_used": [],
  "actions": [
    {
      "type": "button",
      "id": "notify_mentor",
      "label": "Отправить напоминание"
    },
    {
      "type": "card",
      "kind": "ticket",
      "data": {
        "ticket_id": "IT-123",
        "sla_hours": 2
      }
    }
  ]
}
```

Создать расширяемую систему компонентов для отображения `actions`.

Обязательные компоненты:

- ActionButton
- TicketCard
- ChatMessage
- ChatInput
- MessageList
- StreamingMessage

Кнопки должны выполнять реальные действия через API либо явно обозначенные mock-обработчики.

### C. Дашборд наставника

Создать страницу наставника с:

- Таблицей стажёров.
- Именами.
- Процентом прогресса.
- Статусами.
- Списком блокеров.
- Фильтрацией.
- Сортировкой.
- Переходом к чату со стажёром.

Статусы:

- `blocked` — красный.
- `at_risk` — жёлтый.
- `on_track` — зелёный.

Интерфейс должен быть адаптивным.

### D. Роли и маршрутизация

Две роли:

- `intern` — стажёр.
- `mentor` — наставник.

Стажёр не должен видеть дашборд наставника.

Реализуй защиту маршрутов на уровне UI.

Помни, что настоящую проверку прав выполняет Backend. Frontend-защита не заменяет серверную авторизацию.

Для разработки используй временный переключатель ролей.

### E. Обработка ошибок

Предусмотри:

- Backend недоступен.
- AI не отвечает.
- Превышено время ожидания.
- Нет интернет-соединения.
- Ошибка 403.
- Пустые данные.
- Не удалось создать заявку.
- Прерван SSE-поток.

Используй Error Boundaries для ошибок рендеринга и отдельную обработку ошибок сетевых запросов.

Не допускай белого экрана при сбоях.

## 5. Независимая разработка Frontend

Backend разрабатывается параллельно.

Поэтому Frontend должен работать автономно на mock-данных.

Требования:

1. Создай единый слой взаимодействия с API.
2. Отдели UI от получения данных.
3. Используй TypeScript-интерфейсы для API.
4. Реализуй mock-адаптеры.
5. Предусмотри переключение между mock и real API через конфигурацию.
6. Не размещай mock-данные непосредственно в JSX.
7. Не привязывай компоненты к конкретной реализации Backend.
8. Для SSE предусмотрите отдельный mock-поток, имитирующий поступление фрагментов текста.

Желаемый результат: после готовности Backend мы заменяем адаптеры и подключаем реальные эндпоинты без масштабной переработки компонентов.

## 6. API-контракты

Из технического задания известны:

- `GET /api/jira/tasks`
- `GET /api/mentor/interns`
- `POST /api/jira/ticket`
- `POST /api/notify-mentor`

Формат ответа чата описан в спецификации, но конкретный HTTP-эндпоинт и формат SSE необходимо согласовать с Backend.

Не выдумывай отсутствующие контракты и не выдавай предположения за утверждённые решения.

При отсутствии информации создавай временные mock-интерфейсы и отмечай, что нужно согласовать.
